supertool's `edit:@-` op refuses a triple-single-quote-literal `old`/`new` field whose payload
carries an "even run" of backslashes, as a doubling-mistake guard, and offers `literal_backslashes
= true` to exempt it. That flag exempts the field from the *refusal*, but it does not change what
the TOML literal block actually writes to disk: a TOML literal block never processes escapes,
so whatever backslash count you type is the backslash count that lands in the file, verbatim.

The trap: when the edit target is a Python source file containing a real backslash-escape (e.g.
a call to str.replace matching one backslash character -- 2 backslash characters in the .py
source, which Python itself unescapes to 1 at parse time), it is very easy to type the payload
using the *Python-source* byte count you have in your head (already "doubled" once for the Python
escape) and then get "helpfully" told by the refusal to add `literal_backslashes = true`, which
does nothing except pass your (still wrong) count straight through. The two backslash counts that
matter -- "how many characters are in the .py file" vs. "how many characters does Python's own
string-literal parser see after unescaping" -- are easy to conflate, and the refusal message's own
worked example doesn't disambiguate which one it's asking you to halve.

What actually worked, reliably: build the exact byte string in a throwaway python one-liner using
string multiplication of a single-backslash Python literal by N (on the *host* python invocation
used to author the payload, that literal is 1 character, so multiplying by N gives N repeats of
one backslash -- do this counting via a `python3 -c` that only prints, never writes, to sidestep
the separate "python heredoc that writes a file is refused" guard), print the finished TOML payload
to stdout, and pipe that straight into `supertool 'edit:@-'`. Doing this by hand (typing backslash
sequences directly into the heredoc) took three failed round-trips on one function before landing
on the right count; generating the payload programmatically and printing it (never writing with it
directly) got it right on the first try once the counting method was fixed.

One incidental discovery from the same session: the "python heredoc write" guard's regex matches
on the literal text of a write call (e.g. `.write(` or `write_text(`) appearing anywhere in the
heredoc body, including inside a string that is merely being *printed*, not executed as a write.
A `python3 - <<EOF ... EOF | supertool edit` pipeline was refused because the test code being
generated as payload content itself called a write method, even though the outer python invocation
only ever printed to stdout. Worth knowing when authoring payloads whose content is itself Python
source that writes files (as any changelog/test-generation payload naturally will).
